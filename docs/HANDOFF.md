# 핸드오프 — 패스키로 나만의 자리 잠그기 (8번 과제)

작성일: 2026-10-21 · 브랜치: `ai-passkey-on-my-introduction-page` · 이 문서만 읽고 이어서 작업할 수 있도록 적었습니다.

관련 문서: [요구사항 명세서](REQUIREMENTS.md) · [보안 점검 리스트](SECURITY-CHECKLIST.md) · [인증 구현 설명서(제출용)](../AUTH.md)

## 1. 한 줄 요약

1번 과제의 자기소개 페이지(`index.html`, 공개)에 **패스키로만 열리는 "나만의 자리"**를 이어 붙였습니다. 비밀번호는 없고, 서버(Node/Express)가 비공개 자료를 로그인 뒤에만 내려 줍니다. **구현과 실제 기기 확인은 끝났고, 남은 것은 설명서의 사용자 작성 칸, 호스팅·배포, 외부로 올리기 전 보안 점검 결과의 사용자 확인 항목입니다.**

## 4. 실행 방법

```bash
npm install          # 처음 한 번
npm start            # http://localhost:3000, 콘솔에 "첫 등록용 설정 코드" 출력
npm test             # 가상 패스키로 서버 시험 (임시 포트 3100 사용)
```

| 환경변수 | 기본값 | 뜻 |
|---|---|---|
| `PORT` | 3000 | 포트 |
| `ORIGIN` | `http://localhost:PORT` | 서비스 주소. **https 주소면 쿠키에 `Secure`가 붙음** |
| `RP_ID` | ORIGIN의 호스트 이름 | 패스키가 묶이는 도메인. 배포 주소와 같아야 함 |
| `SETUP_CODE` | (없으면 무작위) | 첫 등록용 일회용 코드. 설정하면 고정값, 없으면 등록 한 번마다 새로 바뀌고 콘솔에 출력 |
| `SESSION_SECRET` | (없으면 실행 때 무작위) | 세션 쿠키 서명 키 |
| `DATA_DIR` | `./data` | 패스키 저장소 위치 |
| `LOG_FILE` | `./logs/auth-log.jsonl` | 요청 기록 위치 |

**알아둘 점**
- 패스키는 도메인에 묶입니다. `localhost`에서 만든 패스키는 배포 주소에서는 쓸 수 없습니다. 배포 주소에서 다시 등록해야 합니다.
- 로그인 세션은 30분이고 서버 메모리에 있어, 서버를 다시 켜면 모두 로그아웃됩니다. 화면이 잠겨 있지 않아도 서버는 이미 거절하는 경우가 있습니다(실제로 겪음). 새로고침 후 다시 로그인하면 됩니다.
- 설정 코드는 **첫 패스키가 등록될 때마다 바뀝니다.** 처음 본 코드는 한 번 쓰면 못 씁니다. 서버를 실행한 터미널의 가장 최근 "새 설정 코드" 줄을 보세요.
- `npm test`는 시스템 임시 폴더에 가짜 패스키 저장소를 만들고 지우지 않습니다(보안 점검 S17, 아직 미해결).
- 현재 `npm start`로 띄운 서버가 사용자의 터미널에서 계속 돌고 있을 수 있습니다(포트 3000).

## 5. 구현 방식과 결정 (자세한 표는 REQUIREMENTS.md §2)

- Node.js(Express 5) + `express-session` + `@simplewebauthn/server`(서명 검증)
- 등록: 서버가 질문 발급 → 브라우저 `credentials.create` → 서버 검증 후 **공개키만 저장**. 취소하면 아무것도 저장하지 않음
- 로그인: 서버가 매번 새 질문 → `credentials.get` → 저장된 공개키로 서명 검증 → 세션 새로 발급. 질문은 2분 만료, 한 번만 사용
- 계정 2개, 자료는 **세션의 계정으로만** 정함(주소·본문·헤더에 다른 계정을 적어도 무시)
- 마지막 패스키는 삭제 불가(서버 409). 로그인에 쓴 패스키를 지우면 그 세션도 무효
- 상태 변경 요청은 `Origin` 검사, 설정 코드·로그인 실패는 5분 10회 제한

## 6. 남은 일 (순서대로)

### 사용자가 할 일
1. **스크린샷의 실제 이메일 가리기**: 패스키 저장 위치 선택 창 이미지에 보임(보안 S08, 요구 C12)
2. **취소 화면 확인(C25)**: 패스키 등록 창에서 "취소"를 눌렀을 때 화면에 나오는 안내를 스크린샷으로 보관
3. **계정 B 저장 위치(C26)**: 계정 B 패스키를 어디에 저장했는지 확인해 `AUTH.md` ③ 표에 적기
4. **`AUTH.md`의 `【사용자 작성】` 채우기**: ②, ⑤, 제출문 ②·③, 결과물·소스 URL 등 9곳(`grep -n "사용자 작성" AUTH.md`). **AI가 대신 지어 쓰지 않습니다.**
5. **호스팅 결정과 배포**: 아래 §7 참조
6. **C04~C09 내용 전달**: 원문에서 받지 못한 기준 번호입니다.
7. **올리기 전 결정**: 보안 점검의 사용자 확인 항목 S09, S11, S17, S24, S25
8. **배포 후**: 시크릿 창에서 결과물·소스 URL 열기(C01~C03, C10), 배포 주소에서 패스키 다시 등록, `AUTH.md` 확인 방법대로 점검

## 7. 열려 있는 결정

**호스팅** (미정)

| 선택 | 서버 코드 | 새로 필요한 것 | 패스키 유지 |
|---|---|---|---|
| Render (추천) | 지금 그대로 | 계정 1개, 환경변수 | 무료는 재시작하면 파일이 사라질 수 있음(`AUTH.md` ⑥에 기재) |
| Railway, Fly.io | 지금 그대로 | 계정, 환경변수 | 서비스 정책에 따름 |
| Vercel + Supabase | **고쳐야 함**(서버리스라 메모리·파일이 유지되지 않음) | Vercel·Supabase 계정, 테이블 3개(패스키, 질문, 세션), 환경변수, 행 단위 보안(RLS) | DB에 있어 유지됨. 작업량이 큼 |

- Vercel로 가려면 세션·질문·패스키를 외부 DB로 옮기고 Express를 함수 형태로 바꿔야 합니다. Supabase는 로그인 기능이 아니라 **저장소로만** 쓰고, Supabase의 관리자 권한 키(서비스 롤 키)는 서버 환경변수로만 두며 절대 브라우저·소스에 두지 않습니다.
- 어느 쪽이든 `ORIGIN`, `RP_ID`, `SETUP_CODE`, `SESSION_SECRET`을 배포 환경변수로 설정합니다.
- 심사하는 사람은 패스키가 없어 로그인할 수 없고 "잠겨 있고 직접 요청해도 막힌다"만 확인하므로, 패스키 유지는 필수가 아닙니다.

## 8. 작업 규칙 (사용자 선호)

- **파일 수정·생성·삭제는 먼저 묻고 허락받은 뒤에** 합니다(요청한 파일은 예외).
- **커밋, push, 배포는 하지도 권하지도 않습니다.** 사용자가 직접 합니다.
- **한 번에 하나씩 짧게** 안내합니다. 사용자가 할 일은 단계별로 하나씩, 어디의 어떤 버튼인지까지 구체적으로 알려 줍니다.
- 작업이 끝나면 **요구사항(통과 기준)을 실제로 돌려** 근거와 함께 보고합니다.
- **프로젝트 폴더 밖 변경**(시스템 설정, launchd 등)은 먼저 확인받습니다.
- **지어내지 않습니다.** 받지 못한 기준(C04~C09)이나 사용자 본인의 판단(②, ⑤, 제출문)은 사용자에게 확인하고, 임의로 채우지 않습니다.
- 제출물에 **실제 개인정보를 넣지 않습니다**(이메일, 연락처, 내 컴퓨터 경로 포함).

## 9. 점검 실행 방법

사용자가 **"보안 점검, 요구사항 점검해줘"**라고 하면 다음 순서로 합니다. 하나만 요청하면 해당 점검만 합니다.

1. [SECURITY-CHECKLIST.md](SECURITY-CHECKLIST.md)와 [REQUIREMENTS.md](REQUIREMENTS.md)를 읽는다.
2. 각 항목의 "확인 방법"을 **실제로 실행**한다. 표에 적힌 이전 결과를 그대로 옮기지 않는다. (`npm test`, 명령 모음, 소스 확인, 서버 기록 확인)
3. 사용자만 확인할 수 있는 항목(배포 URL, 스크린샷, 본인 판단)은 ➖로 두고, 무엇을 확인해야 하는지 적는다.
4. 결과를 아래 형식의 **표로 출력**한다.
5. 문서 안의 상태·근거 열과 "최근 점검 결과"는 **사용자 승인 후** 갱신한다.

**상태 표시**: ✅ 통과 · ⏳ 진행중 · ➖ 미확인 또는 사용자 확인 · ❌ 실패

**출력 형식 (요약 한 줄 먼저, 그다음 모든 항목을 한 줄씩 보여 주는 표)**

```
보안 점검 25개: ✅ 18 / ⏳ 2 / ❌ 0 / ➖ 5
요구사항 47개: ✅ 39 / ⏳ 4 / ❌ 0 / ➖ 4

| ID | 항목 | 상태 | 근거 / 해야 할 일 |
|---|---|---|---|
| S01 | 비밀키·토큰이 파일에 없다 | ✅ | 패턴 검색 결과 없음 |
| S17 | 프로젝트 폴더 밖에 파일이 없다 | ➖ | 임시 폴더 2개 발견 → 정리·수정 결정 필요 |
| …  |  |  |  |
```

❌와 ➖는 표 아래에 따로 모아 "무엇을 해야 하는지"를 한두 줄로 적습니다.

## 10. 알려진 한계와 함정

- **못 막은 것(제출용 `AUTH.md` ⑥)**: 모든 패스키를 잃었을 때의 복구 경로 없음, 패스키·세션이 서버 안에만 저장, 패스키 삭제 때 재확인 없음, 시도 제한이 메모리·IP 기준, 설정 코드가 콘솔에 의존.
- **보안 점검에서 남은 것**: 시험의 임시 폴더(S17), 원격 저장소 공개 여부(S25), CSP·HSTS(S23), 설정 코드 콘솔 출력(S12). 실제 기기 기록 파일(`logs/auth-log.jsonl`)은 비밀값이 없어 저장소에 포함하기로 판단함(S11).
- **가상 인증기 시험의 한계**: 실제 패스키 창을 거치지 않습니다. `AUTH.md`에는 실제 기기 기록과 시험 기록을 구분해서 적어 두었습니다(질문 재사용 거절만 시험 기록).
- **Chrome 패스키 선택 창**: 서버에서 지운 패스키도 목록에 계속 보입니다(브라우저는 모름). 고르면 서버가 401 `unknown_credential`로 거절합니다. 이게 C45의 실제 기록입니다.
- **같은 저장 위치에는 두 번째 패스키가 안 들어갑니다.** 서버가 이미 등록된 패스키를 제외 목록으로 보내기 때문입니다. 다른 위치(예: 내 Chrome 프로필)를 고르세요.
- **페이지 확인**: 스크롤 등장 애니메이션 때문에 헤드리스 캡처로는 하단이 비어 보일 수 있습니다. 화면 확인은 실제 브라우저에서 하는 것이 정확합니다. 해상도별 스케일링 규칙(1366px, 1920px)이 있어 `.category` 계열 클래스를 재사용해야 크기가 맞습니다.
- 시험 실행 때 Node의 `ExperimentalWarning`(ML-DSA)이 보이지만 라이브러리가 내는 경고이고 동작에는 영향이 없습니다.
