# 요구사항 명세서 — 10번 과제: AI와 함께 쓰는 첫 논문 작성 (가설에서 결론까지)

> **작성 경위**: 작업 전에 먼저 쓴 문서입니다. 출처는 ① 사용자가 전달한 과제 설명, ② 카드 1~5의 통과 기준(T10-C01~C51), ③ 작업 전에 사용자와 합의한 방향입니다. 통과 기준의 문장은 사용자가 준 원문을 줄여 적었고, 번호는 원문 그대로입니다.
>
> **점검 방법**: "요구사항 점검해줘"라고 하면 항목마다 파일을 직접 열어 확인하고(점검 스크립트를 만든 뒤에는 `node scripts/check.mjs req`도 실행), 사용자만 확인할 수 있는 항목은 ➖로 두고 무엇을 확인해야 하는지 적습니다. 이전 결과를 그대로 옮기지 않습니다. 결과는 요약 한 줄과 항목별 표로 보고하고, 실패가 있으면 이유와 대안을 함께 적습니다. 이 문서의 상태·근거 열은 사용자 승인 후 갱신합니다.

## 0. 주제와 범위

- **과제**: 관심 주제 하나를 골라 AI와 함께 가설을 세우고, 직접 데이터를 모아(직접 돌린 실험 또는 공개 데이터 분석) 검증한 뒤 논문 한 편으로 완성한다. 중요한 것은 근거 있는 결론에 이르는 과정이다.
- **카드 구성**: ① 질문을 가설로(C01~C10) ② 논거 세우기(C11~C20) ③ 실험 설계와 실행(C21~C30) ④ 결과 해석(C31~C40) ⑤ 논문으로 묶기(C41~C51)
- **제출물**: 논문 1편과 재현 패키지를 담은 ZIP 한 개, 그리고 "AI와 나의 판단 3줄". 수료 후에도 남는 포트폴리오다(9번 서사 문서의 포트폴리오 뼈대 자리에 들어간다).
- **주제**: 사용자의 원 문장은 "호칭에 따른 물가 상승과의 연관 관계"이다. 사용자가 정정한 뜻과 현재 상태는 2-2절 아래에 있다. 관심 분야 문장, 후보 열 개와 접은 이유, 최종 가설은 사용자가 정한다(D03).

### 2-1. 내용 점검 규칙 (D11)

**언제 점검하나**: 주제, 질문 후보, 가설, 설문 문항, AI에게 보내는 프롬프트, 결과 해석, 결론, 초록 등 문장을 새로 쓰거나 고칠 때마다 Claude가 먼저 점검한다.

**무엇에 걸리나**
1. 특정 직업·집단·사람을 깎아내리거나 기분 나쁘게 읽힐 수 있는 표현(자격이 없다는 뜻, 허영·착각으로 돌리는 뜻 등)
2. 비윤리적·비도덕적인 방법이나 목적(동의 없는 정보 수집, 속이기, 개인이나 가게를 특정해 비난하기)
3. 근거 없이 원인이나 잘못을 단정하는 문장
4. 고정관념을 강화하는 일반화
5. 개인을 알아볼 수 있는 정보를 받거나 싣는 것(S04, S05, D08과 함께 본다)

**걸렸을 때 Claude가 하는 일**
1. 쓰기 전에 **경고**한다: 어느 부분인지, 누가 왜 기분이 상하거나 피해를 볼 수 있는지를 짧게 말한다.
2. 판단이 들어가지 않는 표현이나 더 나은 방향을 **두 가지 이내**로 제안한다.
3. 사용자와 함께 고쳐서 확정한다. 최종 선택은 사용자가 한다.
4. 사용자가 그대로 유지하기로 하면 그 이유와 유의점을 논문의 한계에 적는다. 다만 특정인을 비방하거나 해를 끼치는 내용은 Claude가 쓰지 않는다.
5. 고친 내용과 이유를 가설 다듬은 과정(C09)과 한계(C39)에 반영한다.

**두 겹으로 적용한다**
- **A. 사용자 메시지마다**: 프로젝트의 `.claude/settings.json`에 UserPromptSubmit 훅을 두어, 메시지를 보낼 때마다 이 규칙을 상기시키는 문구가 자동으로 붙는다. 문구를 붙이는 것까지가 훅의 일이고 걸리는지 판단은 Claude가 한다.
- **B. AI에게 보내는 실험 프롬프트마다**: 실험을 돌리기로 하면, 보내기 전에 프롬프트 목록 전체를 사용자에게 보여 주고 위 5개 기준으로 걸린 부분을 표시한다. 사용자가 승인한 프롬프트만 보낸다. 실험 스크립트를 만들 때 승인 단계를 넣고, 승인 기록(승인한 날짜와 프롬프트 목록)을 남긴다. 실험 방식이 정해진 뒤에 만든다.

**점검을 요청하면**: "내용 점검해줘"라고 하면 위 5개 기준으로 현재 문서의 문장을 읽고, 걸린 부분과 바꿀 안을 표로 보고한다.

### 2-2. 데이터 수집 설계 기록 (D12 상세, 2026-10-28)

**정한 것 (모두 사용자 결정)**

**사용자가 정정한 뜻**

사용자의 원 문장은 "호칭에 따른 물가 상승과의 연관 관계"입니다. 뜻은 다음과 같고 모두 사용자가 정정해 준 것입니다.

- 호칭은 높여 부르는 말입니다(예: 선생님, 아티스트). 한 번이 아니라 오래, 자주 듣는 것을 뜻합니다.

- 직업 범위는 서비스·기술로 돈을 버는 직업입니다. 음식점과 물건 판매는 아닙니다.
- 비교는 항상 같은 직업 안에서 합니다. 직업은 여러 개를 종합해도 됩니다.

**논문 C09에 쓸 재료 (AI와 가설을 다듬은 과정)**

C09는 실제로 오간 되묻기만 적으라고 한다. 이 대화 기록은 새 세션에서 읽을 수 없어서 오간 내용을 여기에 사실만 남긴다. 어떤 판단이었는지의 해석은 사용자가 정한다.

1. Claude가 관심 분야 후보 5개(AI 답변의 일관성, 프롬프트 작성 방식, AI의 할루시네이션, 보안 경고 분류, 공개 통계 겹쳐 보기)를 제안했고, 사용자는 그중에서 고르지 않고 자기 주제 "호칭에 따른 물가 상승과의 연관 관계"를 가져왔다.
2. Claude가 "호칭"이 뉴스 표현, 상품명, 집단, AI 호칭 중 무엇인지 되물었고, 사용자는 물가를 부르는 말과 집단을 합친 것이라고 답했다.
3. 사용자가 호칭은 서비스·기술로 돈을 버는 직종(과외, 미용사, 네일아트, 인테리어)이고 가격 상승은 "가격이 올랐다"는 단순한 뜻이라고 설명했다.
4. Claude가 직종 이름의 품목이 통계에 있다고 가정해 검색했고, 사용자가 "품목이 있을 수 없다, 기술직이고 인건비다"라고 바로잡았다. Claude는 이를 "인건비 비중이 큰 서비스의 가격과 인건비의 관계"로 이해했다.
5. 사용자가 그 이해가 아니라고 두 번 정정했다. 호칭은 높여 부르는 말(예: 선생님, 디자이너)이고, 같은 직업 안에서 호칭만 다를 때 가격이 달라지는지가 궁금하다고 했다. 같은 직업끼리만 비교하되 직업은 넓게 잡을 수 있다고 덧붙였다.
6. 사용자가 "호칭을 오래 듣고 → 자존감이 높아져 → 스스로 가격을 올릴 수 있다"는 흐름을 설명했고, Claude는 자존감을 재지 않으면 검증할 수 없으므로 결론은 "함께 움직이는가" 수준이라고 안내했다.
7. Claude가 AI에게 역할을 주어 답을 보는 실험을 제안했고, 사용자가 "AI가 어떻게 스스로 판단하느냐"고 지적했다. Claude는 AI의 답이 학습된 통념을 재는 것에 가깝다고 인정했고 이 방식을 제외했다.
8. 사용자가 직군을 넓혀 개발자 대 엔지니어도 가능하다는 의견과, 설문은 직업별로 하고 종합해도 된다는 의견을 냈다.
9. 사용자가 주제가 비윤리적이거나 대상이 불쾌할 수 있는지 물었고, 내용 점검 규칙(D11)을 추가해 문서와 훅으로 적용하기로 했다.
10. 데이터 수집 방식 후보를 Claude가 요구사항과 대조했다. 사용자는 미용사가 운영하는 가격표와 디자이너가 운영하는 가격표를 비교하자고 제안했다. Claude는 직함별 보수 자료와 공개 글 분석을 D06·D08·C06 때문에 제외하고, 가격표 비교는 D06 수정을 전제로 남겼다. 사용자가 D06 수정을 승인했다.
11. 사용자가 "미용사 대 디자이너는 너무 일반화되어 있다"고 판단해 직종을 네일로 바꿨고, "수도권은 너무 일반화되어 있다"고 판단해 지역을 대구로 정했다.
12. 사용자가 네일의 호칭을 네일리스트, 네일 아티스트, 네일 선생님, 원장님으로 나눠 알려 주었다. Claude가 원장님은 직책이라 호칭 효과와 섞인다고 지적했고 사용자가 원장님을 뺐다. 이후 사용자가 가게 페이지에서 직접 확인한 분류를 그대로 따르기로 했다.
13. 사용자가 가게 가격 화면을 캡처해 보냈고 Claude가 읽어 CSV로 옮겼다. 같은 가게가 한 번 다시 온 것(A-2)과 같은 브랜드로 보이는 두 가게(B-1, B-8)를 Claude가 짚었고, 사용자가 확인했다.

## 3. 건너뛴 번호

T10-C52 이후는 사용자가 전달한 통과 기준에 없는 번호입니다. 준 것에 없다면 요구사항에 없는 것이므로 점검 대상이 아니며, 지어내서 채우지 않습니다.
